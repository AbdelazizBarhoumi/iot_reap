\section{Network Topology and Segmentation}

To illustrate the practical implementation of the proposed remote access architecture, a network simulation was conducted using Cisco Packet Tracer \cite{cisco-packet-tracer-docs}. The simulated topology reflects a real-world scenario in which strict network segmentation is enforced between the corporate LAN, the virtualization cluster, and external access points.

\begin{figure}[h]
    \centering
    \includegraphics[width=\textwidth]{assets/chapter4/network_topology}
    \caption{Simulated Network Topology — Cisco Packet Tracer}
    \label{fig:network_topology}
\end{figure}

The topology is structured into four distinct network segments, each serving a specific security and operational role:

\begin{itemize}
    \item \textbf{Home/Corporate LAN (192.168.1.0/24):} Represents the end-user environment. Only authorized devices within this segment are permitted to interact with the virtualization layer. Unauthorized devices such as general workstations are explicitly blocked from accessing internal cluster networks through access control lists enforced at the gateway level.

    \item \textbf{VMware NAT Gateway (VNAT-GW):} Acts as the sole entry point between the corporate LAN and the Proxmox cluster network. This device enforces Network Address Translation (NAT) and routing policies, ensuring that the internal cluster addressing scheme (192.168.50.0/24) remains hidden from the broader network, consistent with the principle of least exposure.

    \item \textbf{Proxmox Cluster Network (192.168.50.0/24):} Hosts two Proxmox virtualization servers (PROX1 and PROX2), each managing an isolated VM subnet (192.168.51.0/24 and 192.168.52.0/24 respectively). This segment is entirely unreachable from the public internet and is only accessible through the VNAT-GW, enforcing strict east-west traffic control within the OT-adjacent environment.

    \item \textbf{External VPN Access:} Remote access is simulated through a dedicated external router (R-EXT) connected via an ISP segment. A VPN tunnel (10.10.10.0/30) is established between the external endpoint and the internal gateway, replicating the behavior of a zero-trust network access tool such as Netbird. This ensures that external clients never directly expose or access internal subnet addresses, and all traffic is encapsulated within the authenticated tunnel.
\end{itemize}

This segmented architecture directly addresses the security concerns outlined in the previous section. By enforcing layer-3 isolation between network zones, applying NAT to conceal internal addressing, and restricting external access exclusively through an encrypted VPN tunnel, the design adheres to the core principles of the Purdue model. No direct path exists between the public internet and the virtualization cluster, and lateral movement between network segments is controlled entirely through explicit routing policies and access control lists.

\section{Hosting}

The IoT-REAP platform is deployed on OVH cloud infrastructure at \texttt{iotreap.novationcityapp.com}, providing production-grade hosting with enterprise-level reliability and secure HTTPS access through Let's Encrypt SSL/TLS certificates with automatic renewal \cite{ovh-vps-docs} \cite{letsencrypt-docs}. % CITATION ADDED

\subsection{OVH Hosting Infrastructure}

OVH delivers robust infrastructure supporting the platform's operational requirements through Virtual Private Server (VPS) solution with dedicated multi-core CPU, RAM for concurrent sessions, and SSD storage ensuring optimal database performance.

The server runs Ubuntu 22.04 LTS for long-term stability. Nginx serves as web server and reverse proxy with optimized Laravel settings including gzip compression, browser caching, and rate limiting. PHP 8.4+ with PHP-FPM handles execution using OPcache bytecode caching and optimized memory limits \cite{ubuntu-docs} \cite{nginx-docs} \cite{php-docs}. % CITATION ADDED

MySQL 8.4 operates with production-tuned configurations including InnoDB buffer pool optimization and proper indexing, ensuring sub-50ms query response times. Automated daily backups provide disaster recovery and data integrity \cite{mysql-docs}. % CITATION ADDED

\subsection{Domain Configuration and SSL Security}

The domain \texttt{iotreap.novationcityapp.com} points to the OVH server via DNS A records. Let's Encrypt certificates provide HTTPS encryption for all communications, with Certbot handling automatic renewal \cite{letsencrypt-docs} \cite{certbot-docs}. % CITATION ADDED

Nginx is configured to enforce HTTPS redirection, automatically upgrading all HTTP requests to secure HTTPS connections. Security headers including HSTS (HTTP Strict Transport Security), X-Frame-Options, and Content Security Policy are implemented, protecting against common web vulnerabilities such as clickjacking and XSS attacks \cite{nginx-docs} \cite{mdn-hsts} \cite{mdn-csp}. % CITATION ADDED

\section{Tests and Verification}

The verification of IoT-REAP was conducted at a high level across the main platform workflows. The objective was to confirm that the implemented interfaces, access rules, laboratory services, and learning features behaved consistently together, rather than to document every individual test case.

Functional verification covered the main user journeys, including public navigation, account creation, login, dashboard access, training path discovery, enrollment, unit progression, quiz completion, and certificate consultation. These checks confirmed that learners could move through the platform in a coherent sequence from discovery to practical learning.

Authentication and authorization were also verified to ensure that each role accessed only the interfaces and actions assigned to it. Particular attention was given to the separation between learners, teachers, engineers, and administrators, especially for teaching tools, VM provisioning, infrastructure management, and administrative controls.

The remote laboratory workflow was verified through the creation, access, extension, and termination of VM sessions. The verification also covered the connection between session interfaces and practical resources, including hardware status, camera visibility, gateway availability, and device assignment behavior.

Financial, certification, notification, and teaching workflows were checked at a general level to confirm that payment states, refund requests, certificate generation, user notifications, content creation, analytics, and earnings pages were correctly integrated into the platform experience.

Automated testing complemented manual verification. Backend behavior was checked with PHPUnit for Laravel routes, business rules, and feature flows, while frontend behavior was checked with Vitest for selected React components and interface logic. Together, these tests helped validate both server-side reliability and client-side consistency \cite{phpunit-docs} \cite{vitest-docs}. % CITATION ADDED
